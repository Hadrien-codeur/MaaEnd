# 新版固定滑索送货 P0 实机验收清单

> 2026-09-08：用户确认武陵城滑索布局未变，稍后实测。本表尚无游戏内验证结果。
> 先读 [接力记录](./新版固定滑索送货接力记录.md)确认当前依赖、程序及编译缺项。

## 1. 测试前核对

- 打开的是新版独立目录的测试程序，资源联接指向同一新版仓库。
- 记录源码提交、三个子模块提交、MaaFramework、Go Agent 和 C++ Agent 来源；预编译 C++ 可用于上游原版对照，但不能替代本地编译验收。
- 先处理接力记录中列出的阻塞问题，区分自动化基线缺陷和游戏内问题。
- 使用 Windows 前台控制器 `Win32-Front`。记录游戏分辨率、窗口模式、角色和帧率，检查 HDR 与滤镜；屏幕截图证据换算到 1280x720。
- 确认当前账号和武陵城设施。布局未变是用户确认，仍须以新导入快照核对设施匹配。

## 2. 导入当前设施

1. 在新版任务列表执行“导入/更新滑索坐标”，选择实际区服，由用户登录森空岛或 SKPORT。
2. 读取武陵城相关地图设施；核对设施数量、时间及游戏账号来源。
3. 确认新版 `install/debug/record/Ziplines.json` 已生成，不引用旧安装的快照。
4. 只在本地保留原始导入文件和登录状态，记录快照指纹与验证时间，不提交凭据或完整原始账号数据。
5. 全局“寻路时使用滑索”设为“跟随任务”，保留“始终禁用”作为禁滑回归用例。

当前上游按地图保存设施，未自动隔离账号；换账号必须重新核对。

## 3. 首条武陵城取货空跑

使用当前开发工具连接新版资源及 Agent，在相同传送后站位执行独立路线入口。节点来自 `assets/resource/pipeline/AutoDelivery/Routes/WulingCity.json`：

| 对照 | 现有路线节点 | 预期 |
| --- | --- | --- |
| 上游步行 | `AutoDeliveryRouteDepotDomain2Lv002Depot1` | 走到仓储附近，结束即停 |
| 上游允许滑索 | `AutoDeliveryRouteDepotDomain2Lv002Depot1WithZipline` | 由上游选择路线，结束即停 |

这两个节点只调用导航，无后续取货或提交节点。首次执行前仍须在工具中确认入口和当前覆盖参数。第二个入口“允许滑索”不保证一定选择滑索，不应为了得到想要的结果修改全局成本。

每轮记录：

| 项目 | 待记录内容 |
| --- | --- |
| 版本与环境 | 源码、程序、模型、角色、窗口、帧率 |
| 起点 | 传送点、实际站位、地图与层级 |
| 设施 | 导入时间、快照指纹、来源确认 |
| 路线 | 请求的入口、实际是否用索、上索点与落点 |
| 耗时 | 起步、地面接近、上索、乘索、末段步行 |
| 结果 | 是否到预期仓储、是否仍在架上、人工接管及原因 |
| 证据 | 本地日志及脱敏截图位置 |

先各跑一次定位基本问题，再按计划完成连续空跑门槛。失败时停止，定位具体阶段，不自动循环重跑。

## 4. 后续 P0 和 P1

取货空跑通过后，再对一个武陵城终点做步行与自动滑索对照，随后验证真实委托的取货、送货和交付。记录持货状态、货物损伤与成功后的调用方出口。

P0 需同时满足：可复现环境、本地 C++ 构建、当前账号设施、上游步行与允许滑索的具体路线结果。仅能启动界面不算通过。

P1 首批补齐材料：

- 武陵城取货单跳的起点架、目标架、地面接近段与下索段。
- 一段 2 至 3 跳短链的全部有向架序、楼层和坐标。
- E 接力提示出现、持续、消失和重新出现的证据。
- 末架定位和分叉处实际接力方向。

旧布局未变也不能凭旧首跳、末点和次数推算长链的所有中间架。完整证据不足时，相关路线保持待录状态。
