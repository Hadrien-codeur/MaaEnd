# 多模型开发流程与 OpenSpec 配置交接方案

> 确认日期：2026-11-17。博士已确认采用路径 A：高能力模型规划与审查，DeepSeek 执行，通过仓库文档交接。
> 当前状态：流程方案已确认；OpenSpec 安装、初始化及跨客户端读取验证待 Harness 执行。本文件不是配置完成报告。
> 本轮交付：保存可供后续执行的方案；不安装 OpenSpec，不开发自动派发系统，不启动示例中的自动收菜功能。

## 1. 目标与已确认决策

主要目标是降低高级模型承担全部开发流程的费用，同时保留需求确认、代码审查和实机验收。先使用人工切换客户端与 GitHub 同步，后续有需要再优化自动派发。

| 项目 | 已确认方式 |
| --- | --- |
| 需求讨论、方案设计 | 在当前 Work 会话或同类规划会话中，由博士与高能力模型共同确认 |
| 执行与局部修复 | 在 DeepSeek Harness 中，由 DeepSeek 按已确认文档实施、测试和汇报 |
| 最终评估 | 回到规划/审查端，读取实际代码差异和验证证据，给出结论或修复清单 |
| 需求同步 | 仓库内的需求、设计、任务与交接记录；不依赖跨客户端共享聊天历史 |
| 版本同步 | 本地 Git 仓库执行开发，个人 GitHub 仓库保存交接版本 |
| 规范工具 | 后续采用 OpenSpec；暂不同时引入 GitHub Spec Kit |
| 自动调度 | 暂不配置 CCG、多模型自动派发、看板调度或自建连接程序 |
| 本轮之后的首项执行任务 | Harness 根据本文配置 OpenSpec，再返回此处审查 |

本文中的 Harness 指 DeepSeek Harness；此前讨论中出现的 hardness 为同一客户端的口头称呼。Astra、Opus、Fable 等名称表示候选高能力模型，不是已验证的 API 模型 ID。每个客户端使用实际可用的模型，不能仅凭角色名声称已切换模型。

## 2. 谁负责什么

| 参与方 | 职责 | 交付 |
| --- | --- | --- |
| 博士 | 表达目标、决定关键取舍、提供必要游戏证据、参与实机验收 | 确认范围、补充资料、实测反馈 |
| 规划端高能力模型 | 读取现有项目，消除需求歧义，确定边界、接口、风险和验收条件 | 可执行计划和任务清单 |
| Harness 中的 DeepSeek | 检查基线，按计划配置或编码，运行相关检查，处理局部问题 | 文件改动、检查结果、执行报告 |
| 审查端高能力模型 | 核查需求与实际实现，检查测试有效性和范围偏离 | 有证据的审查结论、具体修复清单 |

规划端负责方案与配置设计；安装、初始化、配置文件修改等执行工作交给 Harness。博士不需要手工设计文档目录或编写工具配置，由模型结合现有规范完成并解释必要选择。

审查默认先报告问题，再交回 DeepSeek 修复；除非博士另有指示，不因发现局部问题就由高能力模型接管整轮实现。

## 3. OpenSpec 在流程中的作用

OpenSpec 提供需求与变更的目录结构、模板、技能和配套命令。它不是独立思考的第三个模型，也不会自动同步两个客户端的聊天或启动 DeepSeek。

实际分工如下：

1. 博士在规划端讨论需求。
2. 规划模型按 OpenSpec 工作方式编写仓库文件。
3. 文件提交并推送，形成明确的计划版本。
4. Harness 读取同一组文件，由 DeepSeek 执行并更新进度。
5. 审查模型对照相同需求检查交付。

初始化只说明工具与目录已准备，不能代表需求已完整、规则已被客户端加载或功能已验收。快捷指令不可用时，可以使用自然语言明确指定文件和工作步骤。

## 4. 项目规则与文档归类

### 4.1 沿用现有规则

配置时读取并引用以下资料，不另写一套相互冲突的编码规范：

- [根目录 AGENTS.md](../../../AGENTS.md)。
- [编码规范](../developers/coding-standards.md)。
- [开发者文档索引](../developers/README.md)。
- [项目开发规范](./新版固定滑索送货开发规范.md)。
- [接力记录](./新版固定滑索送货接力记录.md)。
- 涉及固定滑索时，再读 [已确认开发计划](./新版固定滑索自动送货开发计划.md) 及最新阶段文档。
- 涉及具体模块时，读取仓库内对应的 `.agents/skills/` 说明及组件文档。

以用户当前明确要求和适用项目规则为准。历史计划与最新确认不一致时核查最新记录，不机械恢复已取消的验收门槛。其他功能不照搬固定滑索的业务限制。

客户端个人目录中的技能和聊天历史不一定在另一台电脑存在。必要的项目规则应有仓库内入口；仅引用个人绝对路径不能算完成交接。不得复制 API 密钥或个人配置来解决规则同步。

### 4.2 文档各有一份主要来源

| 内容 | 主要保存位置与用途 |
| --- | --- |
| 本流程与配置交接 | 本文；维护角色分工和工作方式 |
| 项目编码规范 | 现有 AGENTS.md、开发规范及模块文档；其他文件以引用为主 |
| 单次功能需求、设计与任务 | OpenSpec 对应变更目录 |
| 已完成变更形成的长期需求 | 按所选 OpenSpec 版本的归档与规范更新方式维护 |
| 单次执行与审查结果 | 对应变更内的交接报告，记录代码版本及证据 |
| 跨电脑及项目阶段索引 | 现有接力记录；链接详细报告，避免复制全文 |
| 原始日志、缓存和个人资料 | 本机；GitHub 只保留允许提交的摘要及必要脱敏证据 |

预期的变更组织示例如下；初始化时以实际安装版本生成的结构为准，不照搬过期命令或覆盖现有文件：

```text
openspec/
  changes/
    <change-id>/
      proposal.md          提案、范围与不做事项
      design.md            技术方案、约束与风险
      specs/               可验证的需求场景
      tasks.md             实施与验收任务
      handoff.md           本项目补充的执行与审查记录
```

`handoff.md` 是本项目建议的交接文件，不声称它是 OpenSpec 内置文件。归档后保留其可追溯性。本文作为首次配置任务的依据，配置前无需先建立一套虚构的 OpenSpec 变更。

## 5. 每次开发的完整流程

| 阶段 | 工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 需求讨论 | 明确目标、不做事项、正常与异常场景、必要界面证据 | 关键取舍已确认，未知项列明 |
| 方案落地 | 形成需求、设计、任务、验证方法，记录代码基线和计划版本 | 执行任务足够明确；受缺失证据阻塞的任务单独标出 |
| 交给 Harness | 核对目录、分支、本地改动、远端版本，读取规范和计划 | 使用正确版本，保留已有工作，无未解决的基线冲突 |
| 实施与自动检查 | 编码或配置、局部修复、执行适用检查 | 提交可审查结果，清楚区分通过、失败、未执行 |
| 独立审查 | 看需求、实际差异、必要上下文及测试证据 | 问题关闭，或形成明确返工清单 |
| 必要实机验收 | 博士配合测试真实游戏行为，模型分析证据 | 按本任务约定记录结果，不扩大结论 |
| 收尾与同步 | 更新交接记录，按条件归档需求，提交并推送 | 本地与远端提交核实一致，未完成项明确 |

任务状态可以使用“待规划、待资料、可执行、执行中、待审查、需修复、待实机验收、完成”。这是项目约定，不要求 OpenSpec 原生提供同名状态。

### 5.1 执行端何时返回讨论

- 缺少必要截图、ROI、模板、跳转关系或无法确认的游戏行为，不能猜测后写入可执行 Pipeline。
- 实际代码与方案的前提冲突，必须改变接口、架构或需求范围。
- 相同问题在没有新证据的情况下反复修复失败，应提交最小复现、日志摘要及已尝试方法，不无限循环。
- 需要用户作关键取舍或完成实机操作。

普通文件组织、格式化和已有方案内的局部修复由执行端自行完成，不在每个小步骤重复请求确认。需求变化应记录原因并返回规划端确认，不能为了让测试通过而降低验收标准。

### 5.2 交接报告最少包含什么

| 字段 | 要求 |
| --- | --- |
| 任务与状态 | 变更 ID、本轮目标、当前阶段、下一位执行者 |
| 版本 | 远端、分支、执行前基线、计划版本、交付代码提交 |
| 范围 | 已完成内容、修改文件、与原计划的偏差 |
| 验证 | 实际命令、结果、必要摘要、失败和跳过原因 |
| 证据边界 | 区分静态检查、编译、自动测试、游戏空跑、真实业务验收 |
| 未完成项 | 问题、所需资料、下一步动作 |
| 同步结果 | 推送是否成功及核实方式；失败时明确仅保存在本机 |

不要求在提交内容中写入该提交自身的 SHA；可记录已产生的代码提交，再通过后续文档提交或收尾消息给出报告提交。原始日志留本机时，报告应带可理解的结果摘要和复现方法。

## 6. 本地与 GitHub 同步

本地仓库用于文件读写、编译、检查和实机验证；GitHub 保存已提交并推送的交接版本。OpenSpec 文件与代码一起通过 Git 同步，不会自行上传聊天历史。

当前项目约定：

- 公司本地根目录：`E:\MaaEnd V2`。
- 个人远端：`myfork`，对应 [Hadrien-codeur/MaaEnd](https://github.com/Hadrien-codeur/MaaEnd)。
- 上游 `origin` 只读，不作为私人流程文档的推送目标。
- 本文落地分支：`codex/fixed-zipline-delivery`。未来任务记录实际分支，不把该分支误当成所有候选代码的最新业务基线。
- 旧目录 `E:\TestBase2\MaaEnd` 仅作只读参考。

同一台电脑、同一个目录：两个客户端直接看到相同文件，但同一时刻只由一方写入；交接仍提交并推送，便于追溯和另一台电脑接力。

不同目录或电脑：前一方先提交、推送，后一方检查本地状态后拉取。干净且可快进时使用快进同步；存在本地改动或分叉时先保留并核查，不能强制覆盖。开发所需子模块、依赖和程序按实际任务重建，Git 同步不等于运行环境已就绪。

GitHub 同步的是工作文件和版本记录，不是让 GitHub 自动运行模型。后续自动派发另行设计，本阶段不设置后台监听器或自动执行工作流。

## 7. 成本控制

1. 高能力模型集中用于关键需求、设计、复杂阻塞与阶段审查，不持续旁观每条测试输出。
2. DeepSeek 承担实施、相关测试和大部分返工，按一个可独立验收的小功能交接。
3. 文档写到足够执行和验证，不为小修改生成重复长报告；既有规范使用链接。
4. 审查读取交付摘要、实际差异及必要上下文，不重新研究整个仓库；发现风险再扩展检查。
5. 不把每次测试失败都升级给高能力模型，也不让执行端无依据地无限试错。
6. 试跑时记录实际可获得的费用、执行时间、返工轮次和审查结果；拿不到计费数据就标为未知，不承诺节省比例。

## 8. 交给 Harness 的首个任务：配置 OpenSpec

### 8.1 目标与范围

目标是让规划端和 Harness 可以基于同一份仓库需求资料工作。执行端可以安装和初始化必要工具、增加项目指引与配置说明；不开发游戏功能，不引入自动派发，不同时安装 Spec Kit、CCG 或看板系统。

### 8.2 执行清单

- [ ] 阅读本文及第 4 节规范入口，核对本地改动、远端与工作分支；记录开始版本。
- [ ] 检查是否已经安装 OpenSpec、是否已有项目配置及两个客户端的相关集成，保留现有内容，避免重复初始化。
- [ ] 查阅执行时的官方文档，选择并记录明确的 OpenSpec 版本、运行环境要求、安装位置与准确命令。不能将本会话中的示例命令当成永远有效。
- [ ] 在正确项目目录初始化，选择实际支持的客户端集成。优先项目内、可复现配置；必要的用户级工具安装记录位置和恢复方法，不改无关全局配置。
- [ ] 接入 MaaEnd 规范及本文的分工、交接与验收约定。修改 AGENTS.md 时只补必要入口，保留原规则，不整份替换。
- [ ] 配置可使用的需求生成、执行、验证和归档指引。Harness 无原生适配时使用明确的文件读取与自然语言入口，记录限制，不伪称原生支持。
- [ ] 核实客户端实际读取规则的方式。不能假设规划端的技能、聊天、权限或个人路径会自动传入 Harness。
- [ ] 进行最小验证：检查工具版本、配置有效性、变更发现与文档检查能力，并用无业务副作用的示例验证 Harness 能读出范围、规范入口和待验收项。
- [ ] 清理临时验证变更；如需长期保留示例，应说明用途并得到博士确认。不得把示例自动收菜任务登记为正式需求。
- [ ] 形成执行报告：版本、安装位置、修改文件、验证结果、限制、规划端尚需验证的入口及回退方法。
- [ ] 只提交必要项目文件、说明和记录，推送到个人分支并核实；把交付版本交回规划端审查。

执行端本机验证不能替代另一个客户端的实际加载检查。无法操作规划端时，明确标记“待规划端验证”，不得宣称跨客户端闭环已经通过。

### 8.3 配置验收标准

| 验收项 | 通过证据 |
| --- | --- |
| 可复现 | 有明确版本、安装位置和另一台电脑恢复步骤，无凭据进入 Git |
| 规范接入 | 指向仓库有效规则，未覆盖现有规范或复制冲突规则 |
| 文档组织 | 能定位一次变更的范围、设计、任务与交接信息 |
| Harness 可执行 | 实际读取并正确复述测试资料的范围和限制，留下检查结果 |
| 规划端可审查 | 由此处实际确认可读取同一份资料；未验证时保持待办 |
| GitHub 同步 | 交付文件已推送，远端提交与预期一致 |
| 范围正确 | 没有业务代码改动、自动派发或无关依赖升级 |

本任务只涉及文档与工具配置时，运行相应文档、配置和工具检查即可；不为证明配置成功而重新运行全部游戏测试或声称实机功能通过。后续业务代码变更按项目要求运行适用的 `pnpm format`、`pnpm format:go`、`pnpm check`、`pnpm test`、Schema 校验与构建。

## 9. 博士如何发起下一次交接

交给 Harness 时可使用下面的说明：

> 请先检查当前 MaaEnd 仓库的本地改动与个人远端版本，再阅读 `docs/zh_cn/dev-notes/多模型开发流程与OpenSpec配置交接方案.md` 及其规范入口。按照第 8 节配置 OpenSpec，保留现有规则；本轮不开发自动收菜或其他业务功能，不配置自动派发。完成后提供修改文件、工具版本、真实验证结果、未完成项和 GitHub 交付版本，交回规划端审查。

执行后回到规划端时可说：

> Harness 已完成 OpenSpec 配置，请读取本方案及执行报告，核对 GitHub 交付版本和实际差异，验证这里能否读取相同规则与变更资料。先给出审查结论，需要修复的内容形成清单交回 DeepSeek。

## 10. 自动收菜仅作为未来流程示例

示例需求是“收成熟作物，不自动播种，无成熟作物时正常结束”。它尚未正式启动，入口、异常行为、截图、ROI 和模板等仍需另行确认。

未来若启动：在此处确认需求和证据 → 规划模型生成 OpenSpec 变更 → 推送计划 → Harness 拉取并执行 → 推送代码与验证摘要 → 此处审查 → 博士完成必要实机验收 → 更新需求与归档。

不能因为本文件出现这个例子，就安装后直接生成可执行收菜节点。OpenSpec 归档、Git 提交和产品发布是不同动作，均不能替代验收。
