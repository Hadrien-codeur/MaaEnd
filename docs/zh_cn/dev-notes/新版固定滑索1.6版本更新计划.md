# 新版固定滑索 1.6 版本更新计划

> 计划日期：2026-10-17。博士已确认本轮目标是适配游戏 1.6 和近期上游变更，同时保留已经稳定运行的固定滑索送货能力。
> 本文是本轮更新的执行基准。后续实现、验证、安装切换和回滚均按本文顺序进行；如果上游接口或游戏界面再次变化，先更新本文和版本清单，再继续改代码。
> 本轮固定路线只支持武陵地区。四号谷地、试验园区及其他非武陵地区不进入本轮固定路线开发和验收；这些地区继续使用上游普通步行/自动滑索流程。

## 1. 本轮目标和边界

### 1.1 要达到的结果

在 1.6 游戏界面和锁定的最新上游 `v2` 基线上，恢复并验证以下完整链路：

```text
抢委托或转交委托
    → 识别新的 1.6 任务界面
    → 取货/装箱
    → 选择武陵送货终点
    → 进入固定滑索路线
    → 按已确认架序完成逐跳或分段连滑
    → 从实测下索位置接回固定地面段
    → 识别交付对象并提交货物
    → 回到原任务循环
```

固定路线开关默认关闭。关闭时必须回到上游普通导航；未配置固定路线时也必须保留上游行为。固定段已经开始后发生失败，必须明确失败并停止，不能偷偷改走普通路线后记录为固定路线成功。

### 1.2 正式支持范围

本轮兼容清单只登记以下五条武陵固定路线：

| 类型 | 固定路线 ID | 说明 |
| --- | --- | --- |
| 取货 | `wuling_city_pickup` | 武陵仓储取货，作为端到端送货的前置路线 |
| 送货 | `wuling_city_subaiyi` | 苏白易 |
| 送货 | `wuling_city_lind` | 普里莫·林德 |
| 送货 | `wuling_city_yushi` | 玉石 |
| 送货 | `wuling_city_recycle` | 资源回收站/猫头鹰路线 |

送货终点仍以稳定 `source_id` 绑定，不以中文名称、生成文件行号或 JSON 排列位置绑定。当前已知的武陵四个送货 `source_id` 为：

- `deliver_target_map02_lv002_01`
- `deliver_target_map02_lv002_02`
- `deliver_target_map02_lv002_03`
- `deliver_target_map02_lv002_recycle_01`

`test_area_*`、四号谷地以及其他地区的固定路线不出现在本轮正式兼容清单、固定路线选项或验收矩阵中。是否保留这些旧数据文件，只在实现阶段按“隔离而非误接入”的原则处理：可以作为历史参考留在独立归档，但不得生成新的正式 `fixed_route_node`，不得被武陵以外的终点误选。

### 1.3 明确不做的事情

- 不恢复旧 `MapTracker`，不整体搬回旧固定滑索分支。
- 不为四号谷地或试验园区录制、修复、验收新的固定路线。
- 不在 Go Service 中复制送货业务流程；流程仍由 Pipeline 和上游 `AutoDelivery` 负责。
- 不把上游最新生成资源整份覆盖到定制分支，也不把旧生成文件整份覆盖新上游。
- 不在正式安装目录中直接拉取、编译或覆盖文件。
- 不把离线规划、编译通过或旧版本实机结果当作 1.6 实机通过。

## 3. 保护固定滑索开发的总体策略

本轮采用“冻结旧版 → 独立候选 → 分层合入 → 候选验收 → 整包切换”的单向流程：

1. 保留当前已验收安装和代码提交，生成只读版本清单及回滚副本。
2. 从锁定的上游 SHA 创建独立候选 worktree，不在稳定分支和正式安装上操作。
3. 先做上游原版构建和 1.6 UI 兼容，再以适配层形式重新接入武陵固定路线。
4. 把上游同步、UI 适配、固定路线适配、武陵路线数据、测试修复分别提交，禁止混成一个不可追溯的大提交。
5. 测试开始后冻结候选 SHA、子模块、游戏数据快照和生成资源；新的上游提交进入下一轮，不中途改变测试目标。
6. 候选未通过全部门槛前，正式安装和稳定分支均不替换。

建议候选分支命名为 `codex/fixed-zipline-1.6-update-<上游短SHA>`。保留以下提交层次，便于双电脑接力和回滚：

```text
1. upstream-sync-<SHA>       上游源码、子模块和锁文件同步
2. ui-compat-1.6              1.6 界面识别与任务流程适配
3. fixed-route-adapter        固定路线接口对齐上游变化
4. wuling-routes              武陵路线清单、生成数据和文案
5. validation-and-release     测试、清单、安装和回滚记录
```

## 4. 分阶段执行计划

### U0：冻结稳定版、安装和证据

**目的：** 让任何一次 1.6 迁移失败都能回到现在的可用版本。

**工作内容：**

- 检查 `git status`、当前分支、完整 HEAD、个人远端分支和本地安装路径。
- 保存固定滑索代码基线、路线文件、生成目录、Go/C++ Agent 哈希、子模块 SHA、依赖锁文件和控制器限制。
- 为当前正式安装制作完整冻结副本；资源链接、两个 Agent、配置和启动入口必须一起保存。
- 账号配置、设施快照和原始日志只保留在本机，不进入 Git 或公开版本清单。
- 建立“已通过/未覆盖”矩阵，明确旧版证据不能自动继承到 1.6。

**完成标准：**

- 可以在另一台电脑按完整 SHA 找到准确代码。
- 可以启动冻结安装并确认它仍是当前稳定版本。
- 回滚不依赖重新下载上游、重新生成资源或现场重新编译。

**停止条件：** 工作区出现 `outputs/` 之外的改动、正式安装无法定位、哈希或子模块无法确认时，不进入 U1。

### U1：获取并审计 1.6 对应上游

**目的：** 先知道上游实际更新了什么，再决定适配边界。

**工作内容：**

1. 只读检查远端和代理；成功后执行 `fetch origin v2 --prune`，记录完整上游 SHA。网络失败则保留稳定版本，不用陈旧的 `origin/v2` 冒充最新。
2. 在新 worktree 中检出该 SHA，同步递归子模块到主仓库指定指针，按锁文件恢复依赖；不追子模块远端最新。
3. 生成“旧上游 → 新上游”的文件和提交清单，重点查看：
   - `assets/resource/pipeline/AutoDelivery/` 与送货任务 Pipeline；
   - `assets/tasks/SeizeDeliveryJobs.json`、`assets/tasks/DeliveryJobs.json`；
   - AutoDelivery/DeliveryJobs 生成器及 catalog；
   - Go `agent/go-service/autodelivery/`；
   - C++ `agent/cpp-algo/source/MapNavigator/`、滑索状态机和导航数据；
   - Schema、五语言文案、测试集、MaaFramework/MaaUtils/模型子模块。
4. 以 1.6 实机截图和操作录像建立 UI 差异表，至少记录任务列表、任务详情、接单/追踪、传送、仓储、装箱、地图、上索提示、交付对象和提交按钮的旧 ROI、新 ROI、模板、OCR 完整文本及跳转关系。
5. 把无法从源码确认的变化标为“待实机确认”，不能用旧 ROI 猜测新界面。

**完成标准：** 有完整 SHA、差异清单、子模块/依赖记录和 1.6 UI 证据；能明确哪些节点只是坐标变化，哪些节点是语义或流程变化。

### U2：建立上游原版 1.6 基线

**目的：** 把上游问题与固定滑索适配问题分开。

**工作内容：**

- 在候选 worktree 中先不接固定路线，构建上游 Go/C++ Agent 和资源。
- 用 1.6 UI 完成普通步行和普通自动滑索的武陵取货/送货基线。
- 记录任务入口、终点 OCR、传送、取消追踪、取货、交付、回到循环的日志顺序。
- 对已有货物、新装箱货物、非仓储位置恢复分别跑一次上游流程。
- 若上游原版已经无法打开任务或无法完成普通送货，先修复或记录上游阻塞，不把问题带入固定路线适配。

**完成标准：** 上游普通流程在 1.6 至少可进入、可取货、可到达交付点并正常退出；失败可定位到 UI、导航数据或上游逻辑，而不是笼统的“送货失败”。

### U3：适配 1.6 UI 和共享送货流程

**目的：** 先恢复共享 AutoDelivery，再挂固定路线，避免固定路线绕过 1.6 新流程。

**工作内容：**

- 依据 U1 的截图和跳转证据更新 AutoDelivery 识别节点、ROI、模板和 OCR；OCR `expected` 使用完整文本，多语言文本同步维护。
- 更新抢委托和转交委托两套入口的任务详情、传送、取货、送货、交付及结束节点；两套入口继续调用共享 AutoDelivery，不复制流程。
- 检查 1.6 新增或变更的委托门控、已有单恢复、目标名称复核、追踪取消、全局 `Never` 和 `zipline_only` 语义。
- UI 资源和 Pipeline 变更必须保留“识别 → 操作 → 再识别”链，不能用硬延迟掩盖界面变化。
- 新增截图测试时按仓库测试图片规范脱敏；没有截图、ROI 或跳转证据的节点只登记为待补材料，不直接写入生产 Pipeline。

**完成标准：** 关闭固定路线选项时，1.6 上游普通流程与 U2 相同；两种任务入口的节点测试、Schema 和生成器检查通过。

### U4：重新接入固定滑索适配层

**目的：** 只移植固定路线能力，复用新上游的订单、导航和恢复逻辑。

**工作内容：**

1. **路线和生成源**
   - 以 `source_id` 为键，把四个武陵送货终点和武陵取货路线接入新的生成器。
   - 通过 overlay 或稳定构造入口写入 `fixed_zipline_route`、`fixed_approach_path`、`fixed_departure_path` 和 `fixed_route_node`。
   - 重新生成 AutoDelivery、DeliveryJobs 和运行时 catalog；不从旧生成文件整份覆盖新上游。
   - 明确剔除 `test_area_*`、四号谷地及其他非武陵固定路线，确保它们不会产生正式固定节点。

2. **Go 分发**
   - 对齐上游 catalog 和目标解析接口，保留固定开关默认关闭、普通路线回退和终点名称动态清理。
   - 两个任务入口都通过共享 AutoDelivery 按 `source_id` 选择武陵固定节点。
   - Go 只处理目录、参数和分发，不增加订单循环、重试或 UI 流程控制。

3. **C++ MapNavigator**
   - 适配新上游参数解析、导航数据和滑索状态机，只保留固定架序约束、设施唯一匹配、分段连滑、实测落点重接和严格失败语义。
   - 保留普通自动滑索、步行、全局禁滑和上游恢复行为。
   - 固定段开始后无法确认架上状态或落点时停止；不得用最终步行重规划跳过尚未执行的固定段。
   - 复查 1.6 导航网格、地图层级、起步朝向、单向落差边、遮挡/高度判定和下索朝向，不能只复用旧坐标回放。

4. **Schema、任务和文案**
   - 同步 Custom Action/Recognition Schema、AutoDelivery 路线 Schema 和生成器参数。
   - 任务选项仍只在支持的控制器显示；默认关闭，开启顺序保持“送货时优先使用滑索”后再选择“使用已配置的固定滑索路线”。
   - 五语言文案只描述武陵固定路线范围，不把四号谷地或试验园区写成已支持。

**完成标准：** 固定路线契约检查通过；四个武陵送货 `source_id` 与五条路线 ID 一一对应；关闭固定选项、未配置终点、全局禁滑和普通自动滑索均保持上游语义。

### U5：自动验证、构建和离线回归

**目的：** 在接触真实订单前尽可能早地发现接口、资源和状态机回归。

**执行顺序：** 任一步失败即停留在候选 worktree，修复后从该阶段重新执行。

1. JSON/Schema/Prettier 与五语言资源检查。
2. AutoDelivery/DeliveryJobs 生成器检查：生成幂等性、固定节点分发、非武陵不接入、任务选项默认值和目录名称。
3. Go 测试：四个武陵送货 ID、取货 ID、动态目标覆盖清理、已有货物恢复、固定开关关闭、`Never` 和未知路线失败。
4. C++ 固定路线测试：架序唯一匹配、错层/缺架/歧义、单跳、短链、苏白易长链、玉石/回收站分段链、E 预算、落点确认、下索朝向、实测位置重接、取消后状态清理和固定段失败停止。
5. 使用干净构建验证 C++。本机曾出现 MSVC `/showIncludes` 乱码导致头文件修改未触发重编；涉及结构体、头文件或导航接口时必须先 clean，再编译和核对产物哈希。
6. 执行项目规定的 `pnpm format`、`pnpm format:go`、`pnpm check`、`pnpm test`，以及适用的 Go、CMake/CTest、Schema 和送货生成器测试。每项记录目标 SHA 和实际结果，不能沿用旧报告。

**自动门槛：** 所有资源生成、Schema、Go、C++ 和固定路线离线回归通过后，候选状态才可标为 `ready_for_gameplay`；该状态不代表真实游戏验收通过。

### U6：1.6 武陵实机验收

本轮涉及 UI、AutoDelivery、导航和固定状态机，按高影响更新处理。历史七路线结果不继承，实机只验收武陵范围。

#### A. 正常功能矩阵

| 场景 | 必测内容 |
| --- | --- |
| 取货 | 武陵仓储固定取货路线，含单跳/起点接近/取货交互 |
| 抢委托 | 新抢单，四个武陵送货终点逐一覆盖 |
| 转交委托 | 新装箱自送，四个武陵送货终点逐一覆盖 |
| 已有单 | 未取货恢复、已取货恢复、非仓储位置恢复 |
| 路线形态 | 苏白易长连续段、玉石分段、回收站分段、林德长链及四条路线末段下索 |
| 选项 | 固定关闭、固定开启、全局 `Never`、未配置固定路线 |
| 结束 | 交付对象名称复核、提交货物、返回抢单/装箱循环 |

#### B. 异常矩阵

- 设施未导入、缺架、错账号、错地图层级、重复近邻和架序变化。
- 未上架、未起滑、提示持续、多帧重复、漏提示、提前落架、落错架。
- 定位暂失、固定段中途失败、取消后重启、交付目标切换后旧 OCR 条件残留。
- 普通路线和全局禁滑下的步行分流。

每个失败都要记录阶段、路线 ID、任务入口、是否已开始固定段、最终任务状态和日志证据。固定段失败不能继续装箱，也不能返回成功。

#### C. 1.6 UI 验收要求

- 每个发生变化的节点都要有 1.6 截图或录像证据，记录实际 ROI、模板/OCR 文本和下一状态。
- 任务详情、传送、仓储、地图、上索、交付和提交环节都必须完成一次“识别 → 操作 → 再识别”闭环。
- 不能以“点击位置看起来没变”替代识别证据；界面差异未确认时暂停该节点的实机验收。

**实机通过标准：** 四个武陵送货终点在抢委托和转交委托入口均完成至少一轮真实闭环；取货、已有单恢复、固定开关关闭、全局禁滑、未配置路线和固定段失败停止均有独立证据。单条路线成功不能代表整个版本通过。

### U7：候选发布、切换和回滚演练

**候选清单必须包含：**

- 上游完整 SHA、固定适配提交、UI 适配提交和工作区状态；
- 主仓库及递归子模块 SHA、依赖锁文件和 MaaFramework/MaaUtils/模型版本；
- 五条路线文件、生成 catalog、任务资源、两个 Agent 和安装产物 SHA256；
- 控制器范围、自动检查结果、每条武陵路线实机结果和证据路径；
- 本机账号/设施快照位置（只写本机路径或标识，不上传原始内容）。

**切换顺序：**

1. 停止 MXU、Go Agent 和 C++ Agent，确认没有任务运行。
2. 备份当前正式配置，核对候选资源链接已物化，不指向可变源码或稳定安装。
3. 启动独立候选目录，核对实际加载路径、版本、路线清单和 Agent 哈希。
4. 先做一个武陵最小烟测，再允许日常使用。
5. 保留稳定安装和完整回滚副本；回滚时同时恢复资源、两个 Agent、必要配置和启动入口。

Windows 下多次复制文件不视为原子切换。切换和回滚必须各演练一次；演练未完成前不能称为正式发布，也不能删除旧安装。

## 7. 交接、提交和停止规则

每次接力开始：

1. 读本计划、接力记录、开发规范和上次候选清单。
2. 检查分支、未提交改动、远端 SHA、候选 worktree 和正式安装状态。
3. 确认当前候选 SHA 没有在验收期间被悄悄移动。

每次接力结束：

1. 更新接力记录的日期、阶段、提交 SHA、测试结果和未完成项。
2. 运行 `git diff --check`，确认没有账号、原始日志和构建缓存进入提交。
3. 推送个人分支后用远端 SHA 复核；网络失败时保留本地提交并明确标记未推送。
4. 不删除稳定回滚包、失败候选或能解释实机问题的日志索引。

遇到以下任一情况，立即停止当前阶段，保留现场并回到上一个可用候选：

- 上游 SHA、子模块或游戏数据未锁定；
- 1.6 UI 缺少截图/ROI/跳转证据；
- 固定路线与上游普通路线的行为边界无法区分；
- 固定段失败会静默降级或报告成功；
- C++ 头文件变更后未做 clean 构建；
- 生成资源、安装目录或远端分支可能覆盖稳定版本；
- 非武陵路线被重新暴露为固定路线。

## 8. 本计划的完成定义

只有同时满足以下条件，1.6 更新才算完成：

1. 上游最新 SHA、子模块和依赖已记录，候选不是基于陈旧远端引用。
2. 1.6 UI 变化已逐节点核对，普通上游送货闭环通过。
3. 武陵五条固定路线的生成、分发、参数解析、架序、连滑和下索重接通过自动验证。
4. 武陵四个送货终点在抢委托和转交委托两类入口完成真实交付闭环。
5. 固定关闭、全局禁滑、未配置路线、已有单恢复、异常停止和取消重启均有证据。
6. 候选安装可独立启动，稳定安装可完整回滚，版本清单能追溯到所有产物。
7. 更新后的旧开发计划、接力记录和本计划互相链接，明确非武陵路线不属于当前支持范围。

在上述条件完成前，旧版正式安装继续作为日常使用版本；任何“编译通过”“离线规划通过”或“单条路线跑通”的结果，都只能标记为阶段性证据。
