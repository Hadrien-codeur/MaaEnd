### 持续更新的分支与交付方式

采用“已验收基线 → 独立更新候选 → 分层验证 → 晋升”的单向流程：

1. 保留 `de4b06eb` 及其安装作为本次已验收来源，旧稳定安装继续作为第二级回滚。正式冻结时记录资源及两个 Agent 哈希，不将文档保存点当成二进制身份。
2. 新建 `codex/fixed-delivery-update-<上游短SHA>` 候选 worktree，从已验收适配版本出发，将锁定的上游 SHA 合并进去。常规更新保留适配历史，不重写两台电脑共用分支、不强推；结构性重构时才从新上游重建适配层，并逐项核对定制差异。
3. 维护四个边界：独立路线数据、生成器/Schema、Go 的 ID 分发、C++ 固定路线执行扩展。上游负责订单、取货、提交和普通导航。生成结果不作为适配源，不能用旧文件整份覆盖新上游。
4. 合并审查同时比较“旧上游 → 新上游”和“旧上游 → 已验收定制”，记录重叠模块、语义变化和需重测场景。无文本冲突不代表兼容。
5. 测试开始后冻结候选 SHA、子模块和游戏数据。期间的新上游进入下一批；仅将阻塞本轮验收的修复纳入候选，并重跑受影响检查，避免测试目标不断移动。
6. 每次开发接力先检查更新；常规更新建议按周归批，送货/导航关键修复优先评估。本计划不创建后台监控或自动安装任务。

### 自动回归与实机分层

自动门槛按顺序执行，任一失败不晋升：

1. 检查主仓库、递归子模块、锁文件和构建环境；子模块按目标主仓库指针同步，不追子模块远端最新。记录 MaaFramework、MXU、两个 Agent、导航数据和路线版本。
2. Schema 与生成器检查：七终点和固定取货入口、两个任务选项、五语言文案、未配置终点、默认关闭、生成幂等性；确认每个 `fixed_route_node` 实际存在且参数正确。
3. Go 行为测试：关闭/开启、Never、仅滑索可达、未配置终点、目标名称复核与动态覆盖清理；固定导航结束必须接回新版业务链。
4. C++ 生产代码回归：完整架序与 E 预算、提示去重、首跳目标、8+1 分段续行、实际段末架身份、最终下索朝向、实测落点重接保留 RUN、剩余固定段不得被离索步行替代、取消后重启清空、普通单跳/自动滑索不受影响。复用已存在的 `zipline-ride-tests`，补足缺失契约。
5. 在候选独立环境编译。MSVC 调用 `vcvars64.bat` 后设置 UTF-8 代码页，检查 Ninja 头文件依赖确实存在；不能复用已经证明依赖失效的缓存。结构头文件、工具链或依赖改变时用干净构建，并核对 staging 产物哈希。
6. 资源及节点测试按适用仓库规范执行；发布门槛必须有目标提交对应的 `pnpm check` / `pnpm test` 结果，可由 CI 提供。无 PR/无 CI 时明确补齐本地验证安排，不能以“交给 CI”留下空缺。缺图跳过、失败和未运行分别记录。本轮纯文档不运行这些测试。

每次更新都做自动契约检查；实机范围按影响分级：

| 级别 | 条件 | 实机范围 |
| --- | --- | --- |
| 低 | 仅无关任务/文档变化，导航、识别依赖、数据和定制接线均未变 | 两地区各选代表路线，覆盖两任务入口；保留之前完整验收证据 |
| 中 | 送货目录、生成器、任务接线或交付识别变化，导航底座未变 | 所有受影响终点，两任务入口、新单/已有单/持货恢复及普通上游行为 |
| 高 | 定位、网格、滑索规划/状态机、公共运行依赖变化，或影响范围不明 | 七路线、单跳/长链/分段链、两任务入口、异常与取消重启；本次采用此级别 |

异常先用模拟/离线反例验证，再对真实输入、持货恢复和交付补实机证据。缺架、错账号、错层、歧义的启动前处置需单独核实：当前实现不能被描述为已具备统一自动降级。已开始固定段的失败必须停止，不能默默跳过固定段后报成功。

### 安装切换、回滚与版本清单

候选清单至少记录上游完整 SHA、定制完整 SHA、干净工作区状态、路线与生成资源 SHA256、子模块 SHA、锁文件/依赖版本、两个 Agent 哈希、控制器、检查结果以及每条实机用例的日期/状态/证据位置。账号和设施快照仅保存在本机，公开清单不含 UID 或原始日志。

先停止 MXU 和两个 Agent，备份本机配置，再切换完整的不可变版本目录或启动目标；切换前检查硬链接/目录联接，避免候选资源仍指向可变源码或稳定安装。启动后验证实际加载的路径、版本和哈希。回滚必须同时恢复资源、两个 Agent 及必要的兼容配置，不能只换 C++ EXE。上述可回滚切换需演练后才称为完成，Windows 下多次文件复制不等于原子切换。

建议近期执行顺序：先完成 U0/U1/U2，随后做本次高影响上游适配，再安排一次明确范围的实机验收。旧候选继续可用，避免一边补更新机制一边覆盖正在测试的版本。长期可以将通用固定路线接口贡献上游以缩小补丁量，但不作为当前更新的前置条件。

## 1. 结论

方案可行，但必须拆成两个层次：

1. 上游版本作为主基线，负责 MaaEnd 的任务、生成器、MapNavigator、依赖和资源更新。
2. 固定滑索作为独立适配层，按稳定 `source_id` 和明确的 MapNavigator 参数契约重新接入。

不能把当前固定滑索分支的全部提交直接 cherry-pick 到新 `v2`。共同基线 `01ef330a` 之后，当前固定滑索分支有 77 个提交，上游 `v2` 已有 132 个提交；两侧同时修改了 AutoDelivery、DeliveryJobs 和 MapNavigator 的核心文件。

当前已核对的上游最新提交为 `c9204400`。上游已经包含新的滑索子状态机、逐跳账本、账号隔离、AutoDelivery 路径生成和 DeliveryJobs 持货恢复逻辑。迁移时应复用这些能力，只移植固定架序约束和固定路线接口。

## 2. 固定路线接口

固定路线的稳定接口如下：

- 路线文件：`assets/data/MapNavigator/fixed_zipline_routes.json`
- 路线键：固定路线 ID
- 业务键：AutoDelivery 目录中的 `source_id`
- 运行时分发字段：`fixed_route_node`
- 生成源字段：`fixed_zipline_route`
- MapNavigator 参数：`fixed_zipline_route`、`fixed_approach_path`、`fixed_departure_path`
- 业务选项：固定滑索开关默认关闭，只在 `Win32-Front` 显示

七个已验收送货终点和节点名称保存在 [compatibility.json](../../../tools/fixed-delivery/compatibility.json)。更新上游时不得用中文名称、生成文件行号或路线文件位置作为绑定依据。

## 3. 更新顺序

更新流程必须在候选 worktree 中完成，当前安装版本作为回滚基线保留：

```text
检查工作区和当前版本清单
        ↓
获取 origin/v2，记录上游 SHA
        ↓
在临时 worktree 检出上游
        ↓
应用固定滑索适配层和路线 overlay
        ↓
重新生成 AutoDelivery / DeliveryJobs 资源
        ↓
运行接口、Schema、生成器和固定路线测试
        ↓
编译 Go/C++ Agent，执行资源检查和节点测试
        ↓
完成至少一轮武陵城与试验园区正式回归
        ↓
写入兼容清单并原子切换安装目录
```

任一阶段失败都停止在候选 worktree，不覆盖当前安装，不自动把固定路线降级成普通路线后报告成功。

## 4. 兼容检查

候选更新入口为：

```powershell
.\tools\fixed-delivery\stage-upstream-update.ps1
```

该脚本只创建临时上游 worktree、复制固定路线契约、合并路线 overlay 并运行兼容门禁；它不会切换当前分支或覆盖正式安装。当前上游尚未包含固定路线适配层，因此运行到门禁失败是预期结果，候选目录会保留供后续移植。

候选版本的固定路线契约检查入口为：

```powershell
$env:PYTHONIOENCODING = 'utf-8'
python tools/fixed-delivery/check_compatibility.py
python tools/fixed-delivery/check_compatibility.py --json
```

检查内容包括：

- 七条路线 ID 和路线配置版本
- `routes.json` 中的 `fixed_zipline_route`
- 运行时 catalog 中的七个 `fixed_route_node`
- Go catalog / 分发字段
- MapNavigator 固定路线参数解析和执行接口
- AutoDelivery 生成器和两个任务入口的固定选项
- 固定路线与 AutoDelivery Schema

当前固定滑索分支检查通过；直接检查上游 `c9204400` 会失败，这是预期的兼容门禁结果，说明上游候选尚未应用适配层。

## 5. 适配层边界

### 5.1 生成器和资源

固定路线数据应从上游 AutoDelivery 生成结果中以 overlay 合并：

```text
上游 delivery_destinations.json
    -> 上游 AutoDelivery 生成
    -> fixed source_id overlay
    -> WithFixedZipline 路线和 fixed_route_node
    -> DeliveryJobs / SeizeDeliveryJobs 接线
```

overlay 只能写入固定路线字段和经过实测的固定地面段，必须保留上游新增终点、路径修复、语言文案和普通自动规划行为。上游未配置的终点继续使用上游路线。

### 5.2 C++ MapNavigator

最新上游已经承担滑索子状态机、提示消费、逐跳账本、账号隔离和恢复逻辑。固定适配只负责：

- 解析和校验固定路线 ID
- 按设施快照唯一匹配完整架序
- 在规划候选中强制使用作者指定架序
- 执行已经验证的连续段和 E 预算
- 固定段失败时严格停止并输出阶段日志

不得重新引入旧版 MapTracker，也不得复制一套旧的滑索输入循环。

### 5.3 任务选项

任务选项接入必须使用上游生成器的稳定构造入口或适配 hook，不依赖生成 JSON 的行号和具体节点排列。关闭固定路线时，必须恢复上游普通自动滑索；全局禁用滑索时，业务入口继续走上游步行路线。

## 6. 版本清单和回滚

通过候选验证后写入安装目录的兼容清单至少包含：

```json
{
    "upstream_sha": "...",
    "fixed_delivery_adapter": "1",
    "fixed_route_schema": "1",
    "fixed_routes_sha256": "...",
    "generated_catalog_sha256": "...",
    "supported_controller": [
        "Win32-Front"
    ]
}
```

启动或更新时发现清单不匹配、固定路线字段缺失、上游接口变化或构建测试失败，应保留旧安装并提示“需要固定滑索适配”，不能静默覆盖。

## 7. 官方自动更新的边界

`setup-workspace --update` 负责更新开发依赖和已安装组件，不会更新 Git 源码，也不会把本地固定路线注入官方发布包。官方 MaaEnd 发布包同样不能自动携带个人分支的 C++ 和 Pipeline 修改。

因此短期应维护定制更新通道：每次以最新上游构建候选版本，再运行固定滑索适配和验证。长期若希望官方发布包原生保留能力，需要将固定路线接口贡献到上游；路线数据仍需按账号设施快照单独验证。

## 8. 验收门槛

版本迁移完成必须同时满足：

1. 固定路线兼容检查通过。
2. 上游普通 AutoDelivery / DeliveryJobs 回归通过。
3. 七个终点的固定路线节点仍按 `source_id` 正确分发。
4. 武陵城和试验园区各至少完成一轮正式抢委托与转交委托送货回归。
5. 固定开关关闭、全局禁滑、未配置终点和固定段失败停止行为没有回归。
6. 新安装目录可通过兼容清单追溯到上游 SHA、路线版本和生成资源哈希。

在上述门槛完成前，旧版已通过安装不能被自动替换。
